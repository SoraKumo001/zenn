# Remix3とSSR

Remix3はSSRで非同期で取得したデータをシームレスに統合する機能を持っておらず、現在の機能でそれを実装しようとすると、別ファイルのコンポーネントを挿入するためのFrameを強引に使用してやるしかありません。この問題を解決するため、@remix-run/uiのコードを変更して、通常コンポーネントを非同期に対応させる実験を行いました。

# ReactとRemix3の違い

Reactはコンポーネントのステートを記録するのに、グローバル変数を用いています。そのグローバル変数内のオブジェクトにHooksで発生したステートをスタックのように積んでいきます。このせいでコンポーネントの非同期化が出来ません。非同期待ちのスイッチでレンダリング順序が変わると、ステートの順序が狂ってしまうからです。例外としてRSCのサーバーコンポーネントでは非同期コンポーネントを作ることが出来ますが、その代わりステートを一切使うことが出来ません。

これに対してRemix3は、ステート管理にグローバル変数を用いていません。関数内で作られるローカル変数をステート用に使用する形で動作します。このローカル変数を保持するために、コンポーネント関数はReactよりも一回り多層の構造を取ります。この構造のお陰で、レンダリング順序が変わってもステートに対する影響がありません。

# Remix3の標準の非同期コンポーネント

Remix3の標準機能としてFrameコンポーネントを事実上の非同期コンポーネントとして扱うことが出来ます。ただし本来の使用目的は、実行中に外部ファイルからコンポーネントを取ってきて、それをツリー上に組み込むためのものです。そのためFrameに用意されている引数は、対象コードのアドレスを渡すためのsrcを指定するというのが前提になり、通常コンポーネントのようにパラメータを複数設定してレンダリングを行うような用途は前提とされていません。

ただ、Remix3のコードを見てみると、Frameの処理に関してはasync/awaitが使用されており、通常コンポーネントのレンダリング処理もその近くにあります。これはやろうと思えば、通常コンポーネントも簡単に非同期化可能だと想像できます。

# Remix3の通常コンポーネントの非同期化

ということでやってみました。結果としてきちんと動きました。

- 通常コンポーネントをasyncで定義可能にする
- 通常コンポーネントをレンダリング時にawaitで待つ
- 通常コンポーネントのhandleに非同期データ保持機能を追加する
- 保持した非同期データをハイドレーション後に利用できるように転送する

# SSRが簡単になる

非同期コンポーネントによって、コンポーネント単位で非同期データを取得してレンダリングできます。しかもサーバー専用コードではなく、クライアントでも動作するコードとして作ることが出来ます。SSR時はサーバーで、その後のCSRではブラウザからデータを取得するという部分のコードが共通化出来ます。しかもRSCのような境界を考慮した実装がいらないので、データ取得とレンダリングをコンポーネント上に書くだけで好きなように動かすことが出来ます。

ただ、コンポーネント単位で非同期処理を行うと、非同期データを必要とするコンポーネントがネストしたときに、SSRの処理が完遂されるまで時間がかかるという問題が発生します。簡単にはなりますが、そのあたりの考慮を忘れると全体のパフォーマンスが落ちます。

# DPUとの親和性

Chromeで実験的な実装が行われているDPU(Declarative Partial Updates)を使えば、非同期コンポーネントのネストの問題を解決することが出来ます。ReactのRSCのストリーミングをブラウザの機能として行うものです。いずれこのあたりを活用した強力なフレームワークが登場することでしょう。

# 非同期コンポーネントの将来性

非同期コンポーネントの実装ができそうなのでやってみました。結果として、想定通り動作するものになりました。そして無茶苦茶便利です。ただ、本家のRemix3のにこの機能が搭載されることは無いと思います。どこか資金力と人材のある組織が、こんな感じのライブラリやフレームワークを作ってくれると良いなと思うばかりです。
