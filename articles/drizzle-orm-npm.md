# はじめに

Drizzle ORMは、2026年5月22日を最後にnpm上での更新が止まっています。

Drizzle ORMはまだバージョン1.0.0の正式リリースには到達していないものの、直近では `1.0.0-rc` 系のリリースが頻繁に行われていました。そのため、突然npmへの公開が止まったことを不思議に思った人もいるかもしれません。

結論から言うと、これはDrizzle ORM本体の開発が止まったという話ではなく、npmレジストリ側で管理されるパッケージメタデータが肥大化し、リリースを追加できない状態になったことが原因のようです。

# 何が起きたのか

Drizzle ORM公式は、npmのリリースに関する100MB制限に達したため、新しいリリースを公開できない状態だと説明しています。

https://x.com/DrizzleORM/status/2062629339556921581

ここで重要なのは、問題になっているのがパッケージのtarballサイズではないという点です。

npmでは、1つのパッケージに関するメタデータが大きなJSONドキュメントとして管理されています。このメタデータには、パッケージ名やdist-tagだけでなく、これまでに公開された各バージョンの情報も含まれます。

たとえば、各バージョンごとに次のような情報が蓄積されていきます。

- バージョン番号
- 依存関係
- tarballのURL
- integrityやshasum
- 公開日時
- READMEなどの付随情報

つまり、パッケージ本体のサイズが小さくても、公開されたバージョン数が非常に多いと、npmが管理するメタデータの方が大きくなっていきます。

# なぜDrizzleで起きたのか

Drizzle ORMは、正式版だけでなく、beta版やRC版、コミットハッシュ付きのプレリリース版をかなり高頻度に公開していました。

この運用自体は珍しいものではありません。ライブラリの開発では、CI/CDパイプラインを使って、特定ブランチやコミットごとに `rc`、`beta`、`canary` のようなプレリリース版を自動公開することがあります。

しかし、この方法を長期間続けると、npm上のバージョン数が増え続けます。バージョンが増えるたびにメタデータJSONへ新しい情報が追加されるため、最終的にメタデータのサイズ制限に到達してしまうことがあります。

今回Drizzle ORMが直面したのは、まさにこの問題だと考えられます。

# 何が困るのか

この問題でまず困るのは、新しいバージョンをnpmへ公開できなくなることです。

npmへのリリースは、単にtarballをアップロードするだけではありません。npmレジストリ上のパッケージメタデータに、新しいバージョンの情報を追加する必要があります。

メタデータがサイズ上限に達していると、この更新ができなくなります。その結果、Drizzle ORM側で新しいビルドを用意できていても、npm上には公開できない状態になります。

また、メタデータの肥大化はインストールパフォーマンスにも影響する可能性があります。

パッケージマネージャー（npm、Yarn、pnpm）は、依存関係を解決するためにパッケージのメタデータを取得します。メタデータが大きくなるほど、取得やパースにかかる時間、メモリ、CPU使用量が増える可能性があります。

# どうすれば解決できるのか

根本的には、npm上に残っている不要なバージョンを削除し、メタデータを小さくする必要があります。

ただし、npmのunpublishポリシーでは、公開から72時間を経過したパッケージやバージョンを削除するには一定の条件を満たす必要があります。

https://docs.npmjs.com/policies/unpublish/

Drizzle ORMのように利用者の多いパッケージでは、開発者自身で古いバージョンを自由に削除することは難しい可能性が高いです。そのため、Drizzle ORM側はnpmサポートと連絡を取り、対応を進めているようです。

2026年6月10日時点では、npm上の `drizzle-orm` はまだ2026年5月22日を最後に更新が止まっています。新しいバージョンがいつ公開可能になるかは未定です。

# 同じ問題を避けるには

高頻度のプレリリースは便利ですが、npm上に大量のバージョンを残し続ける運用にはリスクがあります。特にCI/CDで自動公開している場合は、メタデータが増え続けることを前提に設計した方がよさそうです。

対策としては、次のような方法が考えられます。

## プレリリース用の別パッケージを用意する

本番利用されるパッケージとは別に、検証用のパッケージを用意します。

たとえば `drizzle-orm` とは別に、`drizzle-orm-canary` のようなパッケージへプレリリースを公開する形です。これにより、本番用パッケージのメタデータを比較的クリーンに保てます。

## 不要なプレリリースを早めに削除する

長期間残す必要のないカナリアリリースは、npmのunpublishポリシー上で削除しやすいうちに削除する運用にします。

CIパイプラインの中で、古いプレリリースを定期的に `npm unpublish` する仕組みを用意しておくと、メタデータの肥大化を抑えやすくなります。

## 別のレジストリを使う

開発途中のビルドをnpmパブリックレジストリにすべて公開するのではなく、GitHub Packagesや社内レジストリに公開する方法もあります。

一般ユーザー向けに配布する必要がないビルドであれば、npm本体に残さない運用の方が安全です。

# まとめ

Drizzle ORMのnpm更新停止は、Drizzle ORM本体の品質や開発状況の問題ではなく、頻繁なプレリリースによってnpmレジストリのメタデータ上限に達したことが原因だと考えられます。

CI/CDによる自動リリースは便利ですが、npmでは「パッケージサイズ」だけでなく「公開したバージョン数」も無視できません。特にプレリリースを高頻度に公開するライブラリでは、メタデータの肥大化を防ぐ運用をあらかじめ考えておく必要があります。
