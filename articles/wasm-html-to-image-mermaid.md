# Mermaidレンダラーの開発が始まった経緯

HTMLをブラウザと同等の精度で画像に変換するライブラリを作っています。Node.jsはもとより、ブラウザやCloudflareWorkersでも動くようにWASMで実装しています。

その過程の拡張機能としてMarkdownをPDFに変換する機能を実装を進めました。そのとき、Mermaidの表示も行おうと思ったのですが、環境に依存せず、かつ多言語フォントのサイズをきちんと解釈し、多用な図表の種類に対応しているライブラリが見つかりませんでした。

どうしようかと頭をひねっていたところ気がつきました。もしかしてHTMLをブラウザ並みにレンダリングできている時点で、図表など簡単に出力できるのではないかと。フォントサイズの計算を含んだレイアウトエンジンはとっくに出来ています。ということでMermaidレンダラーの開発が始まりました。

# 出来上がったモノ

動作が簡単に確認出来るデモをWeb上に作っています。本家のMermaidのようなDOMを必要とする制限はないので、CLIやCloudflareWorkers上でも動きます。

HTMLから画像(アニメーション対応)、画像から画像、MarkdownからPDF、Mermaidから画像のオールインワンパッケージです。画像はWEBP(アニメ対応)、AVIF、新規格のJXLまで対応済みです。全機能、CloudflareWorkersのようなEdge環境で動作します。

# 仕組み: Mermaidの文字列からSVGを組み立てる

Mermaid本体のJavaScriptは使っていません。C++で、Mermaidの文字列を読んでSVGの文字列を組み立てる部分を自前で書きました。エンジンの中は次の流れです。

```text
Mermaid の文字列
  → 図種ごとの解析と配置（C++）
  → SVG の文字列
  → 既存の HTML レンダラー（Skia）で描画
  → PNG / JPEG / WebP / AVIF / JXL / SVG / PDF
```

ラベルの幅は、HTMLを描くときと同じフォントの計測で測ります。ここが最初の狙いでした。日本語のラベルが箱からはみ出したり、箱が大きすぎたりしません。

図を描く側は、出来上がったSVGを普通のHTMLの一部として扱えます。そのため、次のことが追加の作業なしで手に入りました。

- Markdownの ` ```mermaid ` ブロックがそのままPDFに入る。文字は選択できるベクターのままです
- `<div class="mermaid">` をHTMLの中に置くだけで図になる
- 画像形式はHTML変換と同じものがすべて選べる

```typescript
import { renderMermaid } from "wasm-html-to-image/single";

const { data } = await renderMermaid("graph LR\n  A[受注] --> B{在庫あり?}", {
  format: "png",
  theme: "nord",
});
```

コマンドラインからも使えます。`.mmd` ファイルを渡すと、拡張子で出力の形式が決まります。

```bash
npx wasm-html-to-image flow.mmd -o flow.svg
npx wasm-html-to-image flow.mmd -o flow.png --mermaid-theme nord
```

# 図の種類を広げる

最初はフローチャートとシーケンス図くらいのつもりでした。使ってみると、ドキュメントに書かれる図は思ったより種類が多く、少しずつ増やして、今は次の図が描けます。

- フローチャート、シーケンス図、状態遷移図、クラス図、ER図、要求図
- ブロック図（入れ子のブロックを含む）、C4図、アーキテクチャ図
- ガントチャート、円グラフ、棒・折れ線グラフ（横向きを含む）、四象限チャート、レーダーチャート
- サンキー図、ツリーマップ、ベン図、マインドマップ、タイムライン、ユーザージャーニー
- Gitグラフ、カンバン、パケット図、特性要因図、ツリー表示

増やしている途中で、図種ごとに同じ作業を何度もやっていることに気づきました。ノードの色を `classDef` で変える処理は、フローチャート、状態遷移図、クラス図、ER図、ブロック図で必要です。インデントで木を書く記法は、ツリー表示と特性要因図の両方にあります。これらは共通の部品にまとめました。新しい図種を足す作業は、解析と配置を書けば残りは使い回せる形になっています。

`-beta` が付く図の記法は、Mermaid本体でも変わりやすい部分です。自分で確認できた範囲で合わせていますが、本体と完全には一致しません。

まだ描けないのは `zenuml`、`wardley-beta`、`eventmodeling` です。これらは図の位置にエラー枠が出ます。

# 壊れた入力にどう向き合うか

Mermaidの文字列は、人間やAIが書きます。綴りの間違いや閉じ忘れは普通に起きます。そこで、読めない入力に対する挙動を3段階にしました。

| モード | 直すこと |
| :--- | :--- |
| `strict`（既定） | 何も直さない。誤りはエラー枠で見せ、綴りが近いときは `flowchart のことですか?` と候補を添える |
| `compat` | 図種名の大文字小文字、先頭のBOM、CRLF、閉じ忘れた `end` / `}` |
| `recover` | 上に加えて、図種名の綴り違いと、読めない行の読み飛ばし |

大事にしたのは、勝手に直したことを黙っていないことです。直した内容は1件ずつ `onWarning` で受け取れます。

```typescript
await renderMermaid("flowchrt LR\n  A --> B", {
  mode: "recover",
  onWarning: (w) => console.warn(w.code, w.message),
  // MERMAID_RECOVERED: `flowchrt` read as `flowchart`
});
```

読めなかった図は `MERMAID_ERROR` で届きます。コマンドラインでは、同じ内容が標準エラー出力に出ます。図が読めなかったときは、エラー枠の入った画像を書き出したうえで終了コード1で終わります。CIで図が壊れていたら落とす、という使い方ができます。

この仕組みを作る途中で、C++側のログがどこにも届いていないことに気づきました。エンジンのログをJS側のコールバックと診断レポートに流すところから直しています。

# 公式ドキュメントの例で確かめる

自分で書いたテストは、自分が思いついた書き方にしか当たりません。そこで、Mermaidの公式ドキュメントにある書き方に近い110個の例を集めて、「エラー枠にならずに描ける」ことを確かめるテストを作りました。ネイティブのビルドとWASMの両方で流します。

最初に流したところ、11件が失敗しました。

- シーケンス図の `box` / `create` / `destroy` / `link`
- ガントチャートの `until`
- 四象限チャートの `classDef`
- ブロック図で、宣言していない名前を辺で使う書き方
- フローチャートの `A o--o B` と `A x--x B`
- 特性要因図の書き方

どれも自分では書かない書き方でした。11件のうち9件は直し、残る2件（ブロック図の入れ子、横向きの棒グラフ）は「既知の未対応」として記録しました。このリストは新しい失敗が出るか、未対応が直ると失敗するようにしてあります。つまり、直したら必ずリストから消す運用になります。のちにこの2件も実装して、今は未対応が0件です。

# 大きい図は遅い

フローチャートの配置は、層に分けて辺の交差を減らす古典的な方法です。大きな図に対する時間の伸びを測ってみました（開発用ビルドでの測定です）。

| ノード数 | 時間 |
| :--- | :--- |
| 600 | 約11.6秒 |
| 1500 | 約145秒 |

ノードが2.5倍になると時間が12倍になっています。ブラウザの中で動かす用途だと、これは「固まる」と同じです。そこで、アルゴリズムを入れ替える前に、まず上限を付けました。

- 行数: 既定2000行（`maxLines`）
- ソースの大きさ: 既定200000バイト（`maxSourceBytes`）

超えた図は、描かずに「大きすぎます」というエラー枠にします。`0` を渡すと上限が外れます。配置そのものを速くするのは、まだこれからです。

# MarkdownとPDFとの組み合わせ

Mermaidを作り始めたきっかけは、MarkdownからPDFを作る機能でした。そちらも並行して育てています。

前書き（front matter）に、図の色を書けるようにしました。

```markdown
---
title: 設計書
template: report
mermaid_theme: nord
mermaid_mode: recover
---
```

名前で選べるテーマは10種類あり、`nord` や `dracula` などがあります。指定しなければ、ページの色（ライト・ダーク）に合わせた配色になります。

PDFの側でも、図を入れてみて見つかった問題を直しました。

- 1ページより高い `break-inside: avoid` の表が、白紙のページを作る不具合
- 長い表の見出し行が、ページごとに繰り返されること（確認して、テストを足しました）
- ヘッダーとフッターに `{{chapter}}` を書くと、そのページにある `h1` の題名が入る
- 脚注を、参照のあるページの下部に置く（`footnotes: page`）

脚注は、少し変わった作りにしました。ページを区切る処理は「文書全体を1回レイアウトして、決めた位置で切り出す」方式です。ここに脚注を足すために、レイアウトを作り直すことはしませんでした。脚注の本文は文書の末尾に置いたまま印刷せず、ページを区切るときに、そのページで最初に参照される脚注の高さを下部に予約します。描画では、予約した場所に脚注の領域を描き直します。表の見出し行を繰り返す仕組みと同じ道具で済みました。

# つまずいたところ

小さいものばかりですが、種類を挙げておきます。

- **クラス図が空白になった**: `<<abstract>>` のような `<` を含む文字列を、そのままSVGに入れていました。XMLとして壊れて、図全体が出なかった。文字のエスケープを一箇所に集めました
- **ブラウザでWASMが動かなくなった**: WASMを作り直したのに、JS側の部品が古いままでした。埋め込みのWASMを使う仕組みなので、`build` をやり直す必要がありました
- **同じ警告が2回出た**: レイアウトの途中で描画が2回走るため、`onWarning` が同じ内容を2回呼びました。文字列で重複を除いています
- **レイアウトのテストが不安定だった**: 両端揃えの行が、実行ごとに違う区切りの文字列になりました。位置の座標ではなく、ページごとの文字数と先頭・末尾の位置で比べるようにしました

# 全部のテンプレートを「指紋」で見張る

Markdown→PDFには、`report`、`book`、`manual`、`minutes`、`letter`、`slides`、`invoice` など11のテンプレートがあります。CSSを1行触ると、どこかのテンプレートの見た目が変わってしまうことがあります。

画像で比較する方法もありますが、フォントや環境の差で揺れます。そこで、同じ文書を全テンプレートで流して、ページごとに次の値を記録しました。

- ページの大きさ
- 文字数
- 文字が始まる位置と終わる位置

CSSの変更でこの値が動くと、差分としてテストが失敗します。意図した変更なら環境変数を付けて記録し直します。見た目を比べる代わりに、配置が動いたことだけを機械的に気づかせる狙いです。
